## Required behavior

A legitimate zero-match search and a provider failure must no longer be indistinguishable.

Preserve these semantics:

### Valid zero result

When at least one FMP search endpoint successfully returns a valid response and the merged result is genuinely empty:

* return a successful search response
* `results` is empty
* `count` is zero
* do not report a provider failure

### Partial provider success

When one FMP search endpoint fails but the other succeeds:

* preserve and return the successful endpoint’s results
* do not discard partial results
* do not fail the entire request
* log concise diagnostics for the failed side

### Total provider failure

When both FMP search requests time out, raise, return non-success statuses, or return unusable payloads:

* do not silently convert the incident into a valid empty search
* ensure the route exposes a real, machine-detectable provider failure
* use the existing `error: "provider_error"` contract where practical

Audit all consumers before deciding HTTP status behavior.

Preferred behavior, provided no existing consumer requires HTTP 200 for provider failure:

* return HTTP 503
* include a compact JSON error response
* do not expose provider bodies or secrets

If another proven consumer requires the existing HTTP 200 contract, preserve HTTP 200 but ensure `error: "provider_error"` is reliably present whenever both provider paths fail. Explain that compatibility decision in the report.

Do not introduce a generalized status/provenance framework.

## Timeout behavior

Do not blindly increase every timeout.

The backend provider timeout must remain bounded. Verify whether 10 seconds is appropriate based on observed behavior.

The frontend proxy will be corrected separately to allow more time than the backend provider deadline. The backend must return promptly and deterministically once both provider calls have completed or failed.

Keep the two independent FMP calls parallel.
