PROBLEM 1 — WATCHLIST BULK LKG IS NOT TAXONOMY-AWARE
============================================================

The live Watchlist GET has an existing _BULK_LKG cache.

Current version fingerprint is based on Watchlist structural data such as:

  updated_at|ticker_count

A taxonomy assignment does not mutate either field.

Therefore this sequence is possible:

1. GET Watchlist builds/caches row for AXTI with old taxonomy.
2. Canonical taxonomy PUT commits AXTI → packaging_substrates.
3. PUT succeeds.
4. Browser immediately refetches GET /api/watchlist/{id}.
5. _BULK_LKG version still matches.
6. GET returns the OLD cached payload.
7. Browser renders old/unassigned taxonomy.

This must be fixed.

There is already architectural precedent in watchlist_router.py:

PATCH /{watchlist_id}/tickers/{symbol}/theme

explicitly calls:

  _bulk_lkg_invalidate(watchlist_id)

after a theme mutation.

DO NOT revive or switch the editor back to that obsolete mutation route.

Instead, connect the CANONICAL taxonomy PUT to the existing Watchlist LKG
invalidation lifecycle.

Because PUT /ticker-taxonomy/{ticker} does not carry a watchlist_id, invalidate
only existing Watchlist LKG entries affected by that ticker.

Preferred architecture:

- expose a small PUBLIC helper in watchlist_router.py around the EXISTING bulk
  LKG mechanism
- given a ticker/symbol, identify cached Watchlist payload(s) containing that
  ticker and invalidate those entries
- do not globally flush unrelated Watchlists if targeted invalidation is practical
- do not query providers
- do not add another cache/store

IMPORTANT:
Audit the existing _BULK_LKG_BUILDING/background rebuild behavior for an
in-flight rebuild race.

1. invalidate a stale LKG,
2. then have an already-running pre-mutation rebuild finish,
