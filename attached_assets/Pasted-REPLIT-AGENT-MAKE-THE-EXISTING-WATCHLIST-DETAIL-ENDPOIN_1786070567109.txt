# Contract 1 — existing endpoint becomes LKG-first

The browser should not require a full reconstruction before receiving a usable Watchlist.

Implement an LKG/read-model cache for the **final bulk Watchlist response** using existing project cache conventions.

Key it by at least:

```text
watchlist_id
watchlist structural version / updated_at / saved_at or deterministic membership revision
```

Required behavior:

## Valid cached response exists

```text
GET /api/watchlist/{id}
→ return cached complete bulk response immediately
→ if refresh is due, schedule one background rebuild
```

Do not await the rebuild.

## Cache is stale

Return it immediately and rebuild in background.

## Rebuild fails

Keep serving the last valid response.

Do not replace it with an empty/broken snapshot.

## Watchlist membership structurally changes

Invalidate or version-miss the LKG immediately so removed/added tickers cannot remain indefinitely.

Manual add/remove/save flows must explicitly signal the cache.

# Important realtime rule

The frontend already overlays realtime quotes using its realtime quote channel.

Therefore the bulk Watchlist LKG does not need to synchronously hit a provider merely to display the latest intraday price.

However:

* preserve quote provenance
* preserve last-known-good server fields
* preserve 7D/30D calculation semantics
* preserve rank semantics

Choose an appropriately short background rebuild cadence based on current architecture.

Do not invent a long TTL merely for speed.

The goal is:

```text
fast structural/screener snapshot
+
existing realtime quote overlay
```

# Contract 2 — single-flight background rebuild

Only one rebuild for a given Watchlist may run at once.

If ten browser calls arrive while stale:

```text
10 fast LKG responses
1 background rebuild
```

not:

```text
10 full enrichment pipelines
```

Use existing single-flight conventions.

No caller should await an already-running rebuild when usable LKG exists.
