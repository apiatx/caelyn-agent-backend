PROVEN P0 BUG — REQUEST DURING STARTUP WARM
===========================================

Current startup behavior:

`main.py` launches one non-blocking retained Confluence warm through `_start_background_rebuild()`.

That background daemon thread runs:

`build_confluence_snapshot()`

and eventually populates `_RETAINED["snapshot"]`.

However, the current cold/race branch inside:

`get_retained_confluence_snapshot()`

is wrong.

When:

`_RETAINED["snapshot"] is None`

AND

`_RETAINED["build_in_progress"] is True`

the code currently enters an `already_building` branch whose comment says:

"block on one build rather than launching a second one"

but the branch actually executes:

`build_confluence_snapshot()`

again synchronously.

This creates three proven defects:

1. launches a SECOND independent full Confluence build

2. returned result from that racing request build is not retained

3. because async route handlers call `get_retained_confluence_snapshot()` directly, the synchronous ~129-second build freezes the Uvicorn event loop

Production currently runs:

`gunicorn -w 1 -k uvicorn.workers.UvicornWorker --bind 0.0.0.0:5000 --timeout 120 main:app`

The event-loop freeze prevents UvicornWorker heartbeat notification.

Gunicorn can kill the worker after 120 seconds before the ~129-second build completes.

The background daemon warm dies with the worker.

This can create a restart/cold-request loop.

This must be fixed.
