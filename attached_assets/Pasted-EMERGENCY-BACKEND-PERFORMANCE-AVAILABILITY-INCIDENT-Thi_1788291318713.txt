This is not a narrow Watchlist feature task.

The entire CaelynAI site is now failing to load data reliably and/or is extremely
slow. The Watchlist was recently repaired enough to load again, but it is still
very slow, and now unrelated Home-page data sources are also failing at the same
time.

Observed current production UI symptoms:

- Watchlist eventually loads but is extremely slow.
- Home page renders structurally, but unrelated data modules fail together:
  - Macro data temporarily unavailable
  - Risk intelligence temporarily unavailable
  - Daily Alpha Board unable to load
  - Theme data temporarily unavailable
  - Prediction Markets stuck warming/loading
  - Latest News stuck loading
- Top Catalysts can still render.
- This strongly suggests shared backend/runtime contention or starvation rather
  than six independent frontend component regressions.

THIS TASK IS TO PROVE AND FIX THE SHARED PERFORMANCE FAILURE.

Do not blindly increase DB pool size without measuring the pool first.

Use the existing architecture and identify the FIRST EXACT BOTTLENECK.

PHASE 4 — BACKGROUND WORK / THUNDERING-HERD AUDIT
-------------------------------------------------

Inspect whether startup currently launches too much work concurrently.

The backend currently performs a large deferred startup sequence involving DB
initialization, watchlist/theme state, disk LKGs, options universe work, table
ensures, and then numerous periodic loops.

Determine whether the incident is caused by:

- multiple startup jobs competing for PostgreSQL connections
- multiple jobs opening/parsing large files
- several CPU-heavy jobs running simultaneously
- background jobs synchronously blocking the event loop
- live provider calls starting simultaneously
- repeated self-healing/retry loops creating a request storm
- thread-pool starvation
- DB pool starvation
- a combination of the above

Search specifically for retries/polling that can amplify an outage.

Do not just look at Watchlist.

PHASE 6 — FIX THE PROVEN SHARED BOTTLENECK
------------------------------------------

Once the measurements identify the first shared bottleneck, fix THAT bottleneck
using the existing architecture.

Preferred classes of acceptable fixes, only when evidence proves them:

- move remaining blocking synchronous work off the asyncio request/event-loop
  thread
- correctly return DB connections that are being held/leaked
- prevent request paths from unnecessarily waiting for background refresh
- avoid redundant repeated reads already present in the existing request
- stop unintended startup concurrency where two existing jobs are doing
  conflicting work simultaneously
- use existing cached/LKG/canonical state instead of recomputing during an
  interactive request
- bound existing concurrency to the capacity of the existing dependency

A DB pool capacity adjustment is allowed ONLY if:
1. there are no leaks,
2. queries are appropriately short,
3. measurements prove normal legitimate concurrency exceeds max=5,
4. Neon connection constraints are checked,
5. the adjustment is narrowly justified.

Do not use a larger pool to hide leaked/slow connections.
