Fix B — structural freshness fix:
Update stage freshness logic so null stage entries do not stay “fresh” for the full 20 hours.

Current bad behavior:
`{ label: None, score: None, computed_at: recent }` is treated as fresh for 20h even if it came from a failed historical fetch.

Change:

* valid stage label entries keep the normal TTL, e.g. 20h
* null label/null score entries get a much shorter retry TTL, e.g. 2h
* if possible, distinguish true `no_bars` from `fetch_failed`

Preferred:
Add a status field to stage LKG entries going forward:

* `status: "ok"` when stage computed successfully
* `status: "no_bars"` when provider returned no usable historical bars
* `status: "fetch_failed"` when provider call failed, timed out, was blocked, or returned unexpectedly empty during a bulk run

Then freshness rules:

* ok: normal 20h TTL
* no_bars: longer TTL is okay, maybe 20h or 24h
* fetch_failed: short retry TTL, maybe 30–120 minutes
* legacy null entries without status: treat as stale after 2h

Fix C — critical LKG overwrite guard:
Prevent a failed warmup from overwriting the entire stage LKG with nulls again.

Before saving a bulk stage warmup result:

* count total symbols
* count valid labels
* count null labels
* calculate valid coverage %

If existing LKG has valid stage labels and the new run produces an abnormally low valid coverage rate, do not overwrite good values with nulls.

Suggested guard:

* If total symbols > 50
* and new valid stage coverage < 20%
* and previous LKG valid coverage was materially higher
* treat the run as failed / degraded
* preserve previous valid LKG values
* only update entries that produced valid labels
* do not replace valid previous labels with null from this failed run

Per-symbol save rule:

* If new result has a valid label, overwrite old value.
* If new result is null because of fetch_failed, do not overwrite an existing valid label.
* If new result is null because of true no_bars and there was no prior valid label, save no_bars.
* If new result is null because of true no_bars but there was a prior valid label, preserve prior label unless there is strong reason to invalidate it.

This prevents one transient provider/pacing issue from nuking all stage data.
