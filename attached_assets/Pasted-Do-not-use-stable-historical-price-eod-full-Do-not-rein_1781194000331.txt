Hardening pass for thematic Screener Hub refresh behavior after the systemic selected-theme pipeline fix.

The selected-theme pipeline is now mostly correct, but we need to make sure refresh behavior is production-safe and matches product intent.

Product intent:

Default Thematic screen refreshes once per day.
User-selected themes refresh on demand if stale or weak.
Each theme can use FMP at most once per 24 hours.
Refresh caps must survive backend restarts.
Multiple stale theme requests must not spawn 60 simultaneous FMP refresh tasks.
No LLM calls.
No /stable/historical-price-eod/full.
No ETF quote loops.

Part 1 — Audit whether 24h refresh cap is durable

Prevent duplicate refresh tasks for the same theme.

do not start another task
return theme_refresh_status="refreshing"
include same theme_next_refresh_allowed_at if known

Track in-flight per theme safely.

Part 3 — Add refresh concurrency guard

The validation sweep triggered many background refresh tasks and caused resource contention.

Add a safe concurrency guard for FMP theme refreshes:

max 1–3 concurrent theme refreshes

do not spawn 60 simultaneous refresh tasks

Return metadata when queued/skipped:

theme_refresh_status="refresh_queued" or "stale_cap_active"
fmp_refresh_used=false for queued/skipped responses
fmp_refresh_reason explaining why
