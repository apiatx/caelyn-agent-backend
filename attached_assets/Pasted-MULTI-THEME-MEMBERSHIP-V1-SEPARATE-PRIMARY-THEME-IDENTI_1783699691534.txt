MULTI-THEME MEMBERSHIP V1 — SEPARATE PRIMARY THEME IDENTITY FROM ADDITIONAL THEME BASKET MEMBERSHIPS

Work only in the existing backend Replit project.

The multi-theme architecture audit is complete.

The audit proved:

1. `watchlist_category_overrides` is structurally one-to-one per `(user_id, ticker)` and already functions as the canonical highest-precedence manual primary Theme identity.

2. `theme_ticker_overrides` is structurally many-to-many using primary key `(theme_id, symbol)` and already supports simultaneous active add rows for the same ticker across multiple Themes.

3. `ENRICHED_THEME_RS_UNIVERSE` already supports the same symbol in multiple Theme baskets.

4. The Themes-page backend read path naturally exposes a ticker under multiple Theme baskets.

5. Theme RS and Theme Rotation calculate each Theme independently. A ticker in Theme A and Theme B contributes once to each Theme, with within-Theme dedup already present.

6. Options Flow Sectors can expose a ticker under multiple Theme/Sector groupings.

7. All Stocks is globally deduped by ticker and therefore still maintains one canonical ticker row/scan regardless of Theme membership count.

8. The lower Watchlist Theme performance grouping intentionally consumes the one canonical primary Theme and groups each Watchlist ticker exactly once.

9. Current Trade Alignment Theme selection is strictly primary-only through:
   `theme_bridge.get_primary_theme_alignment()`
   → `resolve_primary_theme_for_ticker()`

10. Actionability consumes Trade Alignment and uses hard thresholds. Therefore Trade Alignment Theme-selection semantics must NOT change silently in this task.

The proven architectural defect is:

`POST /api/themes/admin/memberships`

currently treats every Theme basket ADD as both:

* a membership write
* and a primary Theme/classification write

because `_perform_membership_write()` cross-syncs ADD into:

* `theme_ticker_overrides`
* `watchlist_category_overrides`
* `data/llm_theme_overrides.json`

This coupling prevents safe Additional Theme membership.

This task has ONE goal:

FORMALLY SEPARATE ONE CANONICAL PRIMARY THEME FROM ZERO OR MORE ADDITIONAL THEME BASKET MEMBERSHIPS USING THE EXISTING STORES.

Do not add a new database table.

Do not modify Theme RS scoring.

Do not modify Theme Rotation scoring.

Do not modify Options Flow producer logic.

Do not modify All Stocks scan logic.

Do not modify Trade Alignment.

Do not modify Actionability.

Do not modify Entry Structure.

Do not modify Options Alignment.

Do not modify frontend code.

## ADDITIONAL THEME MEMBERSHIPS

A ticker may belong to zero or more additional peer Themes.

Example:

AAOI

Primary Theme:
AI Networking

Additional Theme:
Photonics / Lasers

The ticker should then:

* retain `AI Networking` as the canonical Watchlist primary Theme
* appear under AI Networking on the Themes page
* also appear under Photonics / Lasers on the Themes page
* contribute to both Theme baskets' existing Theme RS / Rotation calculations
* appear in relevant Options Flow Theme/Sector groupings for both memberships
* remain one canonical ticker in All Stocks

Additional Theme membership must NOT:

* overwrite `watchlist_category_overrides`
* overwrite the canonical primary Theme
* write a manual primary classification into `llm_theme_overrides.json`
* change Trade Alignment Theme selection in this task
* cause the lower Watchlist Theme performance grouping to count the ticker twice
