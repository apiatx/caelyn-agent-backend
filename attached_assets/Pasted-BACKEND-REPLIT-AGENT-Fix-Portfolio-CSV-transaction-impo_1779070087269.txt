BACKEND REPLIT AGENT — Fix Portfolio CSV transaction import accounting/classification

The Portfolio Dashboard CSV upload is still parsing/classifying brokerage transactions incorrectly.

Do not model this like the Watchlist CSV upload. Watchlist upload is just a list of symbols. Portfolio transaction CSV upload is an accounting ledger problem.

Current bad examples:
- SIVEF is showing in partially closed, which is true.
- SIVEF is also showing as fully closed in May, which is false.
- SIVEF is missing from open positions, which is false. It should still be open because shares remain.
- OUST and ALMU are showing in partially closed, but they have not been partially closed. They should be fully open only.
- This suggests the importer is classifying rows/months incorrectly instead of netting the full transaction ledger.

Goal:
Support uploading multiple brokerage transaction CSVs to Portfolio Dashboard and produce accurate:
1. Open positions
2. Partially closed positions
3. Fully closed positions
4. Monthly closed-position history
5. Accurate shares, cost basis, realized P&L, remaining shares, average cost, entry/exit dates

Do NOT:
- classify based on one row at a time
- classify based only on a month bucket
- treat any sell as fully closed
- put a ticker in fully closed if shares_remaining > 0
- put a ticker in partially closed unless at least one real sell reduced shares
- overwrite accurate active holdings with bad parse output
- hardcode ticker fixes for SIVEF, OUST, ALMU
- ask user to manually fix the CSV
- change frontend until backend accounting is proven
- break the existing manual add/edit/partial sell logic

Important accounting model:
The importer must build a normalized transaction ledger first, then derive positions from that ledger.

Required pipeline:

Step 1 — Normalize all CSV rows into transactions

Every row should become a normalized transaction object:

{
  transaction_id,
  source_file,
  raw_row_index,
  account,
  symbol,
  trade_date,
  settlement_date,
  action,
  side,
  quantity,
  price,
  gross_amount,
  fees,
  net_amount,
  currency,
  raw_description,
  normalized_type
}

Normalize action/side into:
- BUY
- SELL
- DIVIDEND
- FEE
- TRANSFER
- SPLIT
- IGNORE/UNKNOWN

For now, position accounting only needs BUY and SELL. Other rows should be preserved/audited but not used as buys/sells unless intentionally supported.

Column mapping:
Support common brokerage headers and aliases:
- Symbol / Ticker / Security Symbol
- Date / Trade Date / Activity Date / Transaction Date
- Action / Type / Transaction Type / Activity Type
- Quantity / Shares
- Price / Execution Price
- Amount / Net Amount / Principal Amount
- Fees / Commission
- Description / Security Description

Step 2 — Deduplicate across multiple CSV uploads

Multiple CSVs may overlap. Do not double-count.

Create a stable transaction fingerprint using fields like:
- symbol
- trade_date
- action
- quantity
- price
- net_amount
- raw_description

If brokerage provides a transaction ID, use it. If not, use fingerprint.

Return/import diagnostics:
- total rows
- normalized transactions
- ignored rows
- duplicate rows skipped
- unknown rows requiring review

Step 3 — Sort and build per-symbol ledger

For every symbol:
- sort transactions by trade_date ascending
- if same date, buys before sells unless brokerage order is available
- apply buys/sells sequentially

Accounting method:
Use average-cost accounting for now unless existing code supports tax lots.

Buy transaction:
- increase shares_open
- increase cost_basis
- recompute avg_cost = cost_basis / shares_open

Sell transaction:
- validate shares_open > 0
- shares_sold = quantity sold
- realized_cost_basis = avg_cost_before_sell * shares_sold
- proceeds = shares_sold * sell_price - fees if available
- realized_pnl = proceeds - realized_cost_basis
- realized_pnl_pct = realized_pnl / realized_cost_basis * 100
- reduce shares_open
- reduce cost_basis by realized_cost_basis
- avg_cost remains unchanged for remaining shares under average-cost accounting
- create a closed trade record for sold shares

If sell quantity exceeds shares_open:
- do not silently classify as closed
- flag the transaction as accounting_error / oversell
- preserve diagnostic
- do not corrupt the position

Step 4 — Classify each symbol after processing the full ledger

Classification rules must be based on final per-symbol state:

Open position:
- shares_remaining > tolerance

Partially closed:
- total_sold_shares > 0 AND shares_remaining > tolerance

Fully closed:
- shares_remaining <= tolerance AND total_sold_shares > 0

Never classify a ticker as fully closed if shares_remaining > tolerance.

Never classify a ticker as partially closed if total_sold_shares == 0.

A ticker can appear in both:
- Open Positions
- Partially Closed Positions

A ticker cannot appear in both:
- Open Positions
- Fully Closed Positions

SIVEF expected behavior:
- If CSV ledger has buys and sells but net shares_remaining > 0:
  - Open Positions: YES
  - Partially Closed Positions: YES
  - Fully Closed Positions: NO

OUST expected behavior:
- If CSV ledger has buys and no sells:
  - Open Positions: YES
  - Partially Closed Positions: NO
  - Fully Closed Positions: NO

ALMU expected behavior:
- If CSV ledger has buys and no sells:
  - Open Positions: YES
  - Partially Closed Positions: NO
  - Fully Closed Positions: NO

Step 5 — Monthly closed positions

Monthly closed positions should be based on actual sell/close transactions only.

For each closed trade record:
- month = exit_date month
- include sold shares/proceeds/realized P&L
- fully_closed_month only applies if that sell reduced shares_remaining to zero after processing the ledger

Do not mark a symbol fully closed in a month if a later or remaining open position exists.

Important:
Partial sells belong in monthly realized activity, but that does not mean the entire ticker is fully closed.
