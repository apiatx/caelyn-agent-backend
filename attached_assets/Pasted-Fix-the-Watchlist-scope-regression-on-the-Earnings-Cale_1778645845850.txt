Fix the Watchlist scope regression on the Earnings Calendar.

Backend repo:
apiatx/caelyn-agent-backend

Current user-visible bug:
- All toggle works. Do not change it.
- Watchlist toggle is broken again.
- Watchlist + Day and Watchlist + Week were working before the last Month fix, but are now gone/blank.
- Watchlist + Month still shows the All/curated earnings calendar instead of the user’s saved Watchlist symbols.
- This is getting caused by route/helper regression, not by FMP capacity.

Critical prior working state:
- week-clean?scope=watchlist previously returned real saved Neon watchlist events.
- It used user_earnings_service / user_earnings_cache, not the curated All pool.
- It synced 137 watchlist symbols and cached ~115 user-symbol upcoming earnings events.
- week-clean?scope=watchlist returned 14 real watchlist events for the current week.
- Repeated requests were cache hits with 0 FMP calls.
- All toggle remained unchanged.

Hard rules:
1. Do not touch scope=all behavior.
2. Do not change the curated/thematic All earnings calendar.
3. Do not implement Portfolio in this pass.
4. Do not add historical earnings, EPS actuals, revenue actuals, beats/misses, transcripts, etc.
5. For scope=watchlist, never use or filter the curated All pool.
6. For scope=watchlist, every returned symbol must exist in the saved Watchlist source from Neon/watchlist_service.

Goal:
Restore and lock in correct Watchlist behavior across:
- Day
- Current week
- Next week
- Month
- Next month if navigated

Expected:
- Watchlist + Day: saved Watchlist events for that day.
- Watchlist + Week/current week: saved Watchlist events for current week.
- Watchlist + Week/next week: saved Watchlist events for next week.
- Watchlist + Month: saved Watchlist events for visible month.
- No Watchlist view should show curated All symbols unless that symbol is actually in the user’s saved Watchlist.

Find the implementation that previously made week-clean?scope=watchlist work.

The working behavior was:

- It short-circuits BEFORE curated All logic.
- It loads saved Watchlist symbols from the same service/table used by the Watchlist page.
- It reads user_earnings_service / user_earnings_cache.
- It filters cached forward-window earnings to the requested week/date window.
- It returns the exact same response shape week-clean expects.

Restore this behavior exactly.

Important:
Do not let the new month helper replace or alter the week/day response builder unless it preserves the exact old shape.

Validation before moving on:

- Every returned symbol is in saved Watchlist.
- Zero curated-only symbols.
- All + current week unchanged.

- current week was hardcoded somewhere, or the watchlist helper ignores requested week start/end.

Fix:
- week-clean?scope=watchlist must use the requested from/to or weekStart/weekEnd params from the frontend.
- Filter the same forward-window user_earnings_cache to that exact requested week.

Validation:

- Next week request returns next week Watchlist events if they exist.
- If next week is empty, prove by checking cached forward-window events that no Watchlist earnings fall inside that requested next-week date range.

Step 6 — Use one source of truth, but not one broken response builder
It is okay to share the data loader:
- load saved Watchlist symbols
- read user_earnings_cache
- filter by date range

But do not force Day/Week/Month into one generic response builder if the frontend expects different shapes.

Preferred architecture:
- shared helper returns filtered watchlist earnings events:
  get_watchlist_earnings_events_for_window(from_date, to_date)
- route-specific builders then shape those events for:
  - day/week clean response
  - month-all response
  - month-curated response

This avoids breaking week while fixing month.
