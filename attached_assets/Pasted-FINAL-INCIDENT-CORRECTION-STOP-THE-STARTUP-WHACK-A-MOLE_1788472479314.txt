- 51 focused tests pass
- yet first health failure begins around process age 46.8s
- that is BEFORE Terminal prewarm
- it now coincides with the +45s calendar snapshot startup task

This pattern itself is now the root-cause evidence.

Do NOT patch Calendar next in isolation.

The systemic problem is that heavyweight initial refresh/catch-up jobs are independently
scheduled throughout the first several minutes of process life.

The API currently has no single authoritative rule saying:

"interactive serving has priority; heavyweight startup refreshes must not overlap."

We are fixing THAT.

PHASE 2 — CLASSIFY STARTUP WORK
==================================================

Classify each job into exactly one of these startup classes.

CLASS A — REQUIRED HYDRATION

Cheap work necessary to make persisted state usable.

Examples:
- load existing LKG/cache from disk
- cheap canonical state reads
- import/router readiness

Requirements:
- no large provider fanout
- no full-universe crawl
- no hundreds-of-symbol history refresh

These may run near startup, using existing to_thread patterns where synchronous.

CLASS B — OPTIONAL HEAVY REFRESH

Anything performing:
- provider fanout
- full-universe scan
- hundreds of symbols
- large RSS crawl
- large history refresh
- expensive scoring/rebuild
- SEC/Whale crawl
- large background database work

These MUST NOT compete during the critical interactive startup period.

CLASS C — DUPLICATE STARTUP REFRESH

A job whose recurring scheduler/loop will refresh the same canonical state shortly anyway.

Do NOT perform an extra startup catch-up merely because historically one existed.

If persisted LKG/cache is available, use it until the canonical scheduler runs.

Do not create a replacement cache.
