# Contract 2 — every non-sector node needs an effective sector rollup

The preceding report says only seven nodes received `rollup_sector_ids`:

* five promoted parent themes
* Clean Energy
* Data Center Infrastructure

That leaves descendant subthemes potentially without their own rollup-sector metadata.

This creates a functional hole:

* Gold belongs under Metals & Mining.
* Metals & Mining rolls up to Materials.
* A stock may have only `theme_ids=["gold"]`.
* A Materials filter matching only IDs directly listed under Materials would not match that stock.

The frontend must not need undocumented label heuristics or hidden inheritance assumptions to make basic sector filtering work.

## Required canonical rule

Every node with classification `theme` or `sub_theme` must expose a non-empty effective `rollup_sector_ids` list unless it is explicitly and intentionally market-wide.

Use this resolution order:

1. Explicit `rollup_sector_ids` on the node.
2. Otherwise, the node’s valid canonical `parent_sector`.
3. For a subtheme with `parent_theme_id`, include the parent theme’s effective rollups as inherited values.
4. Preserve any valid explicit cross-sector additions.

The final exposed list must be:

* canonical sector IDs
* deduplicated
* deterministic
* cycle-safe
* never display labels

This can be represented explicitly in every registry node or computed through one canonical helper used by response serialization. Do not create parallel implementations in multiple endpoints.

Prefer keeping `rollup_sector_ids` semantically complete in the canonical registry or a single canonical registry helper. Do not make the frontend reconstruct registry semantics.
