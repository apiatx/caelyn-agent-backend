# Contract 6 — rebuild the atomic assignment architecture correctly

The existing endpoint:

```http
PUT /api/themes/admin/ticker-taxonomy/{ticker}
```

currently calls `_perform_membership_write()` repeatedly.

That is not atomic because `_perform_membership_write()`:

* writes one membership
* may cross-sync the primary theme
* invalidates caches
* triggers side effects

Do not use that helper repeatedly inside the atomic endpoint.

## Trace the actual persistence architecture first

Identify exactly where these are stored:

```text
primary assignment
additional memberships
category_overrides
theme_ticker_overrides
theme_ticker_mapper / LLM overrides
manual provenance
```

Determine which stores share the same Neon transaction and which do not.

If a true all-or-nothing operation cannot be implemented without a new table or major architecture change:

* stop
* report the exact obstacle
* do not claim the operation is atomic

Do not create a second source of truth.

## Required endpoint semantics

One request:

```json
{
  "primary_theme_id": "dc_connectivity_silicon",
  "additional_theme_ids": [
    "networking_fabric_infra"
  ]
}
```

must result in exactly:

```text
Primary:
dc_connectivity_silicon

Additional:
networking_fabric_infra
```

The requested primary must never depend on set iteration order.

Additional memberships must never write into or overwrite the primary store.

## Required processing order

1. Authenticate.
2. Normalize ticker.
3. Validate all taxonomy IDs.
4. Normalize:

   * remove duplicates
   * remove primary from additional
   * remove redundant ancestors
5. Read authoritative current state.
6. Begin one transaction or proven rollback-safe unit of work.
7. Set or clear primary explicitly through the canonical primary path.
8. Diff and update additional memberships through the canonical additional-membership path.
9. Preserve manual provenance.
10. Commit only after all writes succeed.
11. On any failure:

    * rollback all writes
    * return failure
    * do not continue
12. Invalidate caches exactly once after success.
13. Trigger downstream noncritical hints only after successful commit.
14. Return the authoritative final reread.

Do not:

* catch one membership failure and continue
* return `ok=false` after partial mutation
* invalidate caches once per membership
* call a primary cross-sync for every additional membership
* determine final active memberships by searching every theme basket containing the ticker
* infer explicit assignments from `proxy_symbols` or `candidate_symbols`

## Final response

Return:

```text
ticker
sector_id when available through the established company-sector source
primary_theme_id
additional_theme_ids
theme_ids with primary first
subtheme_ids
memberships_added
memberships_removed
```

`theme_ids` must be:

```text
primary first
then normalized deterministic additions
```

Do not alphabetically move the primary away from the first position.
