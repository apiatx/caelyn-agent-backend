BACKEND — CANONICAL HISTORY SAFE-MODE HARDENING

Backend only.

Do not revert the canonical history cache.
Do not remove Stage / Entry / Fib integration with canonical cache.
Do not rewrite the Tradier limiter.
Do not touch options flow.
Do not touch frontend.
Do not change Confluence scoring.

Goal:

The canonical history implementation is acceptable, but it must be locked down so it cannot accidentally consume Tradier capacity during market hours or repeatedly refetch full historical data.

Important correction:

The canonical history target should be up to 10 years of daily candles, not 5 years.

If a stock has less than 10 years of trading history, fetch as far back as the provider has candles, effectively back to IPO/listing date.

If a stock has more than 10 years of history, cap canonical history at 10 years because older data is not useful for the current Stage / Fib / Entry / Extension system and wastes calls/cache.

We want:

1. One-time full 10Y backfill allowed manually/off-hours.
2. Cached bars always used instantly after backfill.
3. No request-time provider calls.
4. No automatic full-watchlist Tradier history jobs during market hours.
5. No recurring full 10Y refetches just because TTL is stale.
6. Incremental daily append only after the initial cache is built.

==================================================
PART 1 — CONFIRM NO AUTO-RUN
==================================================

Audit and confirm:

- canonical_history_backfill does not auto-run at startup
- canonical_history_backfill does not auto-run during retained snapshot rebuild
- canonical_history_backfill does not auto-run from frontend/page requests
- canonical_history_backfill only runs from explicit admin endpoint or scheduled off-hours job

Return exact file/function evidence.

If any auto-run exists, disable it.

==================================================

==================================================

Add/confirm these env/config flags with safe defaults:

CANONICAL_HISTORY_BACKFILL_ENABLED=false
CANONICAL_HISTORY_FULL_BACKFILL_ENABLED=false
CANONICAL_HISTORY_INCREMENTAL_APPEND_ENABLED=true
CANONICAL_HISTORY_ALLOW_MARKET_HOURS=false

Behavior:

If CANONICAL_HISTORY_BACKFILL_ENABLED=false:
- admin/status endpoints still work
- cache reads still work
- no provider calls are made

If CANONICAL_HISTORY_FULL_BACKFILL_ENABLED=false:
- no full-history fetch is allowed
- except manual force endpoint with explicit mode=manual_rebuild and confirm=true

If CANONICAL_HISTORY_ALLOW_MARKET_HOURS=false:
- full backfill and append jobs do not run during market hours
- return paused_market_hours instead of calling provider

==================================================
PART 3 — ONE-TIME FULL 10Y BACKFILL MODE
==================================================

Full historical fetch should only happen when:

- admin endpoint explicitly requests mode=initial_full_backfill or manual_rebuild
- CANONICAL_HISTORY_BACKFILL_ENABLED=true
- CANONICAL_HISTORY_FULL_BACKFILL_ENABLED=true
- market is closed unless explicitly forced
- symbol does not already have available_10y or actual_ticker_history_limit
- provider call goes through scheduler
- no raw httpx bypass

Target:

canonical_history_target_years = 10
canonical_history_requested_days = 3650
preferred_bars = approximately 2520 trading bars
minimum_5y_bars = 1100
minimum_10y_bars = 2200

After a symbol reaches available_10y:
- do not full-refetch on normal runs
- do not full-refetch because TTL is stale
- mark it complete

If symbol has fewer than 10 years of public trading history:
- classify as actual_ticker_history_limit
- cache all available history
- do not treat it as provider failure
- do not keep trying to fetch older nonexistent bars

==================================================
PART 4 — CHANGE TTL SEMANTICS
==================================================

Current report used available_5y → 20h TTL.

Update this for 10Y history.

TTL/staleness should mean “needs append check,” not “cache invalid.”

Change semantics:

available_10y cache remains valid even if older than 20h.
Stale means:
- needs incremental append check
- not unusable
- not full refetch required

Add statuses:

available_10y_fresh
available_10y_needs_append
available_10y_stale_but_usable
available_5y_partial_long_history
available_3y_partial_history
actual_ticker_history_limit
cache_corrupt_needs_rebuild

Rules:

- Stage/Entry/Fib can use available_10y_stale_but_usable.
- Stage/Entry/Fib can use actual_ticker_history_limit when the ticker is genuinely newer than 10 years.
- Only cache_corrupt_needs_rebuild should trigger manual full rebuild.
- Missing 1–3 recent bars should trigger incremental append, not full fetch.

==================================================
PART 5 — INCREMENTAL DAILY APPEND ONLY
==================================================

After initial full backfill:

Daily maintenance should:

- run off-hours only
- fetch only from newest_bar_date - 2d to today
- one request per symbol max
- skip if newest_bar_date is already current
- merge by date
- write after each symbol
- never fetch 3650 days in incremental mode

If the report currently says “≈2 Tradier calls/symbol/day,” clarify/fix:
- target should be 1 history request per symbol per append run
- with 2-day overlap inside that one request

Set:

weekly_health_check:

monthly_full_refresh:

- manual/admin only

- If only 400 bars exists, use it only as fallback and enqueue backfill.
