CURRENT BUG 2 — BACKGROUND REFRESH LOCK CAN LOSE A MUTATION
===========================================================

Current code uses roughly:

```
if not _BG_REFRESH_LOCK.acquire(blocking=False):
    return
```

The comment claims the running refresh automatically incorporates all newer
commits.

That is NOT guaranteed.

Race:

1. Save A commits.
2. Refresh A starts and reads Neon.
3. Save B commits after Refresh A's DB read.
4. Background task B sees the lock.
5. Task B returns / skips.
6. Refresh A writes an enriched universe that contains A but not B.
7. No refresh remains queued for B.

Fix this without restoring concurrent refreshes.

============================================================
REQUIRED COALESCING SEMANTICS
=============================

Maintain exactly one expensive refresh worker at a time, but NEVER drop the fact
that another mutation occurred.

Use the smallest robust generation/dirty mechanism.

Preferred shape:

* module-level monotonically increasing refresh generation or dirty counter
* every successfully committed taxonomy mutation increments/marks it
* background worker acquires single-worker lock
* records generation being refreshed
* performs refresh_enriched_universe()
* after refresh:
  if generation advanced while refresh was running:
  refresh again
  else:
  exit
* a background task that finds the worker already running should mark the
  generation/dirty state and return; the active worker is responsible for
  catching up before exiting

Important race:

Before the worker finally exits, the "is dirty?" check and release/worker-exit
must be coordinated so a mutation cannot arrive between:

```
check clean
→
worker exits
```

and become stranded without a future refresh.

Use a lock/generation pattern that makes this atomic.

Do not create Redis, a queue service, another scheduler, or DB table.

This is a tiny in-process coalescing worker for the CURRENT single-worker Uvicorn
architecture.
