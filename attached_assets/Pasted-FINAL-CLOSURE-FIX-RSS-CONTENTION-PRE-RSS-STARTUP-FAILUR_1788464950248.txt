CURRENT RSS ARCHITECTURE
========================

Current code:

- _TARGET_INTERVAL_S = 120

- thread count spiked during the sweep
- the sweep overlapped the slow active Watchlist/Home matrix

This means the RSS subsystem is nearly continuously doing large full-universe work.

Do NOT replace the RSS architecture.
Do NOT add a queue system.
Do NOT add a new scheduler.
Do NOT change the news endpoint contract.
Do NOT add providers.

Apply narrow corrections to the EXISTING sweeper.

1. OFFLOAD WATCHLIST MEMBERSHIP READS

run_rss_sweep() currently performs synchronous:

list_watchlists()

and per-watchlist:

load_watchlist(...)

from inside the async event-loop path.

Move these existing synchronous reads off the event loop using the project's existing
asyncio.to_thread / run_in_executor pattern.

No new data source.
No new membership cache.
public.watchlist remains canonical.

2. BOUND RSS CONCURRENCY MORE CONSERVATIVELY

The current concurrency of 15 is too aggressive in the shared application runtime.

Reduce the ticker sweep concurrency enough to preserve event-loop/request responsiveness.

Start with:

_SWEEP_SEM_SIZE = 8

Do not increase it during this task.

Yahoo and Google fetches remain concurrent for a given ticker.

3. SEPARATELY BOUND SYNCHRONOUS DATABASE WRITES

Do not allow every active ticker worker to simultaneously occupy the default executor with
upsert_with_cache().

Add a small in-sweep semaphore around ONLY the existing synchronous archive-write dispatch.

Maximum concurrent RSS archive DB writes:

4

This is NOT a new worker system.
It is simply a concurrency bound around the existing call:

upsert_with_cache(ticker, merged)

Provider fetch concurrency and DB-write concurrency should be independently bounded.

4. GUARANTEE BREATHING ROOM BETWEEN FULL SWEEPS

Current scheduling:

wait = max(0, TARGET_INTERVAL - elapsed)

means an 88.7-second sweep under a 120-second target gets only ~31 seconds idle.

If a sweep ever exceeds the target, the next sweep effectively begins immediately.

That is unacceptable for a background archive-maintenance job.

Preserve the existing loop, but ensure there is a meaningful minimum idle period after each
completed full sweep.

Use:

minimum post-sweep idle = 60 seconds

Do not begin another full sweep sooner than 60 seconds after the prior sweep completes.

Keep the existing 120-second target semantics where possible, but the minimum idle floor wins.

Example:

wait = max(MIN_IDLE, TARGET_INTERVAL - elapsed)

Do not introduce a separate scheduler.
