If you switched from a gated Grok 4.2 path back to Grok 4.1 Fast Reasoning in the backend, and the frontend was untouched, but the same Social button still throws the same 402, then the most likely issue is not the frontend. It is one of these:

1. Your running backend is still serving the old code.
If the frontend calls a deployed backend URL, changing code locally in Replit does nothing until that backend is restarted or republished to the environment the frontend actually uses.

2. That Social button is hitting a different backend code path than the one you edited.
This is very common. One route/helper was changed, but the button actually calls a different prompt handler, provider wrapper, or fallback path.

3. The request is using an xAI tool/model combination that still requires access on that path.
xAI currently documents model-specific behavior and agent-tool paths separately. Their docs also show grok-4-1-fast as a valid model family and note that grok-4-1-fast does not use the reasoning_effort parameter, while newer Grok 4.20 variants have separate reasoning/tool behavior. xAI also documents x_search as a built-in tool path, separate from plain text generation.

The release notes also show Grok 4.1 Fast and agent tools evolving as separate platform capabilities, which supports the idea that “switching the model name back” does not guarantee you fixed the exact failing code path if that button is still using an agent/tool route.

Your own project notes support that this app uses Grok/xAI for X sentiment and analysis and expects an XAI_API_KEY in Replit, so the error is almost certainly happening inside the xAI-backed Social pipeline rather than some generic frontend bug.
