## Current proven state

The Watchlist regression itself is fixed.

`get_comparison_closes_bulk()` now reads compact 64-session comparison tails from the in-memory canonical `_INDEX` and performs:

* zero request-time gzip opens
* zero full-history JSON loads
* zero provider calls
* zero database calls

The published deployment currently contains an `_index.json` with valid comparison tails for 426 canonical symbols.

However, the durability audit proved:

1. Older canonical gzip payloads generally do not contain `comparison_close_tail`.
2. `_rebuild_index_from_gz()` cannot recreate tails from those payload metadata alone.
3. If `_index.json` is lost, rolled back to the pre-repair state, or reconstructed from older gzip payloads, comparison closes return null.
4. There is no automatic off-request migration that repairs missing tails.
5. Autoscale filesystem-write persistence across every instance lifecycle remains unproven.

The goal is to add a small, idempotent, post-yield self-healing path.

## Required design

### Part 1 — Add a canonical tail validator

In `canonical_history_service.py`, add one narrowly scoped internal validator for `comparison_close_tail`.

A valid tail must:

* be a non-empty list
* have no more than `_COMPARISON_TAIL_SESSIONS` entries
* contain entries shaped as `[date_string, positive_finite_close]`
* use valid ISO dates
* be chronological
* contain no duplicate dates
* contain only dates strictly before the current New York market date when newly generated

The validator must not perform disk I/O or provider calls.

Do not make request-time comparison selection depend on expensive validation of every entry. This validator is for metadata maintenance and repair selection.

### Part 2 — Tighten the existing repair skip condition

The current `backfill_volume_metrics_metadata()` skip condition accepts any entry merely containing the `comparison_close_tail` key.

Change it so the repair skips a symbol only when:

* all required existing Watchlist market metric fields are present
* the comparison tail passes the validator

An empty, malformed, oversized, nonchronological, duplicate-date, or otherwise invalid tail must be repaired.

Preserve its existing behavior:

* existing canonical gzip files only
* no providers
* no database
* no new table
* no new endpoint
* no alteration of historical bar values
* one `_write_index()` after successful updates
* normal no-op behavior when nothing needs repair

### Part 3 — Add an idempotent self-heal helper

Add one public service helper with a clear name such as:

```python
ensure_comparison_close_tails()
```

Use the repository’s naming conventions if another name fits better.

This helper must:

1. Ensure `_INDEX` has been preloaded using the existing path.
2. Select only canonical symbols eligible for repair.
3. Call the existing `backfill_volume_metrics_metadata(symbols=...)` path only for those selected symbols.
4. Return structured counts suitable for bootstrap logging and tests.

A symbol is eligible for startup tail repair only when:

* it has an `_INDEX` metadata dictionary
* its canonical metadata indicates at least `_RECENT_MIN` usable bars
* its status is usable under the existing canonical-history contract
* its canonical `{SYMBOL}.json.gz` file exists
* its tail is missing or invalid

Do not select:

* `TEST_*` artifacts unless they independently meet the real canonical eligibility contract
* dotted legacy keys
* foreign-prefixed symbols
* excluded symbols
* `fetch_failed`
* `not_yet_backfilled`
* `insufficient_history`
* `cache_corrupt_needs_rebuild`
* entries without a canonical gzip file
* metadata-only placeholders
* symbols already holding a valid tail

Do not hard-code a list of 426 symbols.

The helper should return at least:

```python
{
    "selected": int,
    "updated": int,
    "file_reads": int,
    "skipped": int,
    "missing_after": int,
    "elapsed_ms": int,
    "status": "noop" | "repaired" | "partial" | "error",
}
```

Additional useful fields are allowed if kept compact.

### Part 4 — Wire it into the existing post-yield bootstrap

In `backend/main.py`, use the existing `_post_yield_bootstrap()` path.

The repair must run:

* after canonical `preload_index()` succeeds
* after the FastAPI lifespan has yielded
* through `asyncio.to_thread(...)`
* without blocking the event loop
* without delaying the health/root endpoint from becoming available
* before the bootstrap declares itself complete

Do not add a second startup framework or scheduler.

Add an isolated bootstrap step similar to the existing timed steps.

Recommended behavior:

```python
from services.canonical_history_service import ensure_comparison_close_tails

result = await asyncio.to_thread(ensure_comparison_close_tails)
_BOOTSTRAP_STATE["steps"]["comparison_tail_repair"] = {
    "ok": result["status"] != "error",
    **result,
}
```

Follow the existing bootstrap logging and error-isolation conventions rather than copying this literally if local code differs.

A repair failure must:

* be logged clearly
* be recorded in `_BOOTSTRAP_STATE`
* remain nonfatal to application startup
* not abort unrelated bootstrap steps
* not restore request-time gzip scanning

### Part 5 — Avoid repeated and competing work

The normal current deployment already has 426 valid tails.

On that state, startup repair must:

* select zero symbols
* open zero gzip files
* write no index file
* finish as a fast no-op

Do not run `backfill_volume_metrics_metadata()` blindly against all 496 index entries.

Do not run the repair once per HTTP request.

Do not add a repeating timer.

Do not add a daily repair when all tails are valid.

Do not create a separate global cache.

If the canonical maintenance scheduler can begin concurrently with the post-yield repair, inspect its actual startup timing.

Ensure the repair does not create unsafe duplicate work with:

* incremental canonical append
* missing-history catch-up
* full canonical backfill
* `_write_index()`

Prefer sequencing the one-time repair immediately after canonical index preload, before other canonical maintenance performs writes.

Do not introduce a broad new locking architecture unless repository evidence proves it is required.

If a narrow existing lock or sequencing mechanism already exists, reuse it.
